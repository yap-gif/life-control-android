## Design decision (candidate only)
Use ordered per-collection immutable chunks and one flat manifest. Each chunk binds collection, sequence and rows by canonical UTF-8 SHA-256; the derived logical key includes the hash. Manifest contains workspace header, all collection counts, ordered refs (key/hash/bytes/count) and whole-workspace digest. Reassembly requires a separately trusted manifest digest, explicit positive max value size, exact refs/counts/order, complete chunk set and full domain validation. Hashes are integrity checks, not authentication. No data discarded, no partial workspace returned. Invalid/oversize record or index fails closed. Empty collections have zero chunks. 16 KiB and 1 KiB etc. are synthetic test caps, not measured APS limits. Limit accounts for canonical JSON value bytes only, not key/envelope/metadata overhead or aggregate quota.
 
## Scope / future publication protocol (NOT IMPLEMENTED)
Keep planner in qa/sharding only; no integration into repository, UI, deployed bundle, storage, SDK or remote services. A future design requires verified atomic create of immutable chunks, exact readback, single root-pointer CAS with an independently authenticated root, post-CAS readback, durable operation receipts and bounded recovery. No root creation, orphan deletion, garbage collection, overwrite or legacy migration in L04. Readers must retain previous complete snapshot or stop if referenced chunks missing; do not fall back silently. Flat manifest cannot scale indefinitely: hierarchical index or a different model must be designed if actual limit exceeded. Content-addressed keys leak equality and hashes do not provide encryption; privacy, retention/erasure and key format limits require review before any real storage. No claim of atomic multi-key writes, exclusivity, real capacity or crash recovery.
